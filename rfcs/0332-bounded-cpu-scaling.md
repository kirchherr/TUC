# RFC 0332: Bounded CPU scaling

Status: implementation in progress; installed/static/sanitizer observations,
final CI and owner review remain required.

## Problem and decision

The current CPU path can multiply equal-sized tensors, but a caller must
duplicate a single scaling factor or feature-gain vector to the full output
shape. This obstructs compact scaled attention and affine feature calibration.
Extend the existing neutral `elementwise_kind="mul"` interpretation with two
explicitly bounded right-hand shape cases, without introducing another family,
source evaluation or backend-specific IR attribute.

The useful compositions are `Softmax((Q @ K.T) * scale) @ V` and
`Softmax(((X * gain) + offset) @ W.T + bias)`. The former is a single-head,
unmasked scaled attention calculation. The latter applies fixed supplied
calibration parameters, not learned normalization or a model-loading protocol.

## Shape contract and inspectability

All tensors are FP32 with rank one or two; the output is fresh and has the
left input's shape. Shape classification is ordered:

1. Equal left and right shapes preserve the existing elementwise product.
2. Otherwise a right `[1]` tensor supplies one shared factor.
3. Otherwise left `[M,N]` with right `[N]` supplies a factor per column.
4. All other combinations reject.

Thus `[1] * [1]` remains the old product, while `[M,1] * [1]` is the single-factor
case. There is no rank-zero value, literal scalar, operand reversal, column-vector
expansion, dynamic shape, dtype promotion or general broadcast engine. Source
syntax remains multiplication between two known tensor names. JSON admits no new
attributes. Source Intent, semantic validation, reference execution and movement
planning apply the same shape contract before emission or execution.

HAC-IR retains hardware-neutral `ELEMENTWISE`/`mul`. Movement plans count actual
compact input bytes and expose scaling interpretation without materializing an
expanded factor. Existing equal-shape planning notes and program digests remain
unchanged. Dimensions 1-64, eight operations, 24 tensors, 1,000,000 logical scalar
work units and 256 KiB tensor storage remain. Multiplication costs one logical
work unit per output element, independent of factor storage size.

A dedicated CPU-only artifact schema `tuc.bounded_scaling_dag_artifacts.v0`
normalizes new cases to `mul_scalar` (opcode 8) and `mul_row_scale` (opcode 9).
It requires at least one actual unequal-shape product and composes every
previously supported CPU operation, including Softmax. Source dispatch chooses
it before the Softmax emitter only for such graphs. Existing emitter schemas,
generated bytes, program identities and retained observations remain scoped to
their original graphs. CUDA or mixed target selection rejects for this extension.

## Arithmetic and runtime boundaries

Each result is one checked binary32 multiplication, using RHS index zero for
the shared factor and `i % N` for per-column factors. Existing FE_TONEAREST,
MXCSR, no-FMA and normal-or-signed-zero rules remain. Nonfinite or subnormal
products, and nonzero operands whose product rounds to zero, reject. Exact
signed-zero products remain valid. No algebraic reordering or implicit dtype
conversion is introduced.

Short, long or overlapping compact factor descriptors reject before reads.
All arithmetic uses owned scratch; returned errors preserve public outputs
under the existing live-buffer/no-concurrent-mutation preconditions. Existing
binary framing, explicit local Docker execution, per-request isolation and
batch failure behavior remain unchanged. No new runtime permission or library
is needed. Softmax compositions retain RFC 0331's checks and corpus tolerances.

## Security and validation

The added input surface is a small shape-admission extension. Validation must
agree across isolated source parsing, canonical Source Intent, typed lowering,
reference semantics, movement plans, primitive emission and checked entrypoints.
Tests cover malformed/hostile objects, reversed/ambiguous shapes, output aliases,
budget exhaustion, unsupported targets, corrupted artifacts and legacy identity
stability. Existing pointer-liveness and concurrent-access limits still apply.

A separate standard-library installed consumer owns six source programs in two
profiles: direct scaling, calibrated classifiers and scaled attention. Two
datasets per program plus one three-request shared-parameter batch produce
82 checked outputs: 22 bitwise FP32 scaling values and 60 composed values under
Softmax tolerances. Twelve public probability rows receive mass checks. Eight
source/JSON rejection controls and four numerical controls include a failing
last batch request with no partial result JSON.

A separate native harness covers scalar-vector scaling, matrix/feature scaling,
scaled attention and calibrated classification. Static and ASan/UBSan builds
each require 16 successful case runs, 134 total calls, 92 scalar checks,
118 rejected calls and 677 unchanged-output checks. Pure scaling uses bitwise
comparisons including signed zero. Composed results use absolute tolerance
`2e-6` plus relative tolerance `2e-5`; classifier row mass must be within `8e-6`.
Three deliberately faulty checkers and invalid invocation must fail per build.
These are fixed-corpus criteria, not global error or performance bounds.

CI uses existing hash-locked dependencies, pinned read-only actions, offline
wheel builds and installation outside checkout. Original observations must bind
source, wheel, consumers, contexts and image identities before native execution
is claimed. Synthetic candidates and unit tests remain separate from observations.
No GPU, general Triton/PyTorch equivalence, production or performance claim is made.
